# docker-publish, csharp-publish and npm-semantic-release have no step-level tests

## Status — partially remediated 2026-08-07

`npm-publish` is now covered by `_tests/unit/npm-publish/behavior.spec.sh`
(9 examples through `run_step`; the dist-tag mutation that motivated this
finding is caught). The finding stays **open** because the rest of its scope is
not done: `docker-publish`, `csharp-publish` and `npm-semantic-release` still
have no step-level tests. It closes when those three are covered.

## Problem

Defect class: coverage-hole + mutation-blind.

At the time of filing, only 4 of 28 test directories exercised action step logic
via the harness (`run_step` / `run_all_owned_steps`): `ansible-lint-fix`,
`docker-build`, `_harness`, `release-monthly` — now 5, with `npm-publish`. The
remaining publishing actions (`npm-semantic-release`, `docker-publish`,
`csharp-publish`) have validation specs only. Those specs call
`validate_input_python`, which exercises `kit.CHECKS`, not the action's `run:`
blocks, so no production shell logic in them executes anywhere in the suite.

## Evidence

The `npm-publish` case below is the worked example that proved the defect class
real; it is now fixed and is retained as the template for the three actions that
remain. `npm-publish/action.yml:220-239` — dist-tag selection, untested as filed:

```sh
# Determine dist-tag: use prerelease label (e.g. "beta" from "1.0.0-beta.1") or "latest"
prerelease_label=$(printf '%s' "$sanitized_version" | sed 's/^[^-]*-\([^.]*\).*/\1/')
if [ "$prerelease_label" != "$sanitized_version" ] && [ -n "$prerelease_label" ]; then
  dist_tag="$prerelease_label"
else
  dist_tag="latest"
fi
...
npm publish --registry "$REGISTRY_URL" --verbose --tag "$dist_tag" --scope "$PACKAGE_SCOPE"
```

Mutation spot-check as filed: invert the comparison on the `if` line (`!=` -> `=`).
`1.0.0-beta.1` then resolved `dist_tag=latest` and `1.0.0` resolved
`dist_tag=1.0.0`, and the suite result was unchanged. All 37 `It` blocks in
`_tests/unit/npm-publish/validation.spec.sh` are `validate_input_python` calls
against `kit.CHECKS`; `_validation/tests/` never executes an action's `run:` block
(`test_generate.py` runs `validate.py` standalone, nothing else). No test failed.

Since 2026-08-07 that same mutation fails 8 of the 9 examples in
`_tests/unit/npm-publish/behavior.spec.sh`. The identical spot-check has **not**
been run against `docker-publish`, `csharp-publish` or `npm-semantic-release`,
which is what keeps this finding open.

`release-monthly` is the counter-example that proves the class matters: it is one
of the 4 with a step-level test, and that test is what surfaced the live
production defect in finding `tests-c1051f2d`. The same defect class in a
validation-only action would be invisible.

## Impact

A mutation or regression in publish-time logic reaches production undetected.
For the mutation above, every prerelease publishes to the `latest` dist-tag, so
`npm install <pkg>` serves a beta to every consumer, and every stable release
publishes under a garbage dist-tag. Equivalent untested branches gate
`docker-publish`'s push, `csharp-publish`'s `dotnet nuget push`, and
`npm-semantic-release`. These are supply-chain paths where the blast radius is
every downstream consumer, and the suite is green through all of it.

## Fix

Add `behavior.spec.sh` step-level tests for the publishing actions.
`npm-publish` is **done** — the pattern below is what shipped, and it is the
template for the three that remain. The harness already supports everything
needed: `npm`, `docker` and the other network CLIs are in
`MockRegistry.BLOCKED_COMMANDS`, so each is shadowed and must be mocked
explicitly, and an unregistered call exits 127 rather than passing silently.

Remaining work, each needing its own `behavior.spec.sh`:

- `docker-publish` — push gating (`push: ${{ inputs.push }}`) and tag construction
- `csharp-publish` — the `dotnet nuget push` gate
- `npm-semantic-release` — release/plugin resolution

Note that a step must have an `id:` for `run_step` to target it; `npm-publish`
needed one added. Expect the same for the three above.

```sh
It "publishes a prerelease under its prerelease dist-tag, not latest"
export INPUT_TOKEN="ghp_aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
export INPUT_PACKAGE_VERSION="1.0.0-beta.1"
mock_command npm "publish * --dry-run *" ""
mock_command npm "publish * --verbose --tag beta *" ""
When call run_step "${ACTION_DIR}" "<publish-step-id>"
The status should be success
The stdout should include "beta"
End

It "publishes a stable version under latest"
export INPUT_PACKAGE_VERSION="1.0.0"
mock_command npm "publish * --verbose --tag latest *" ""
...
End
```

The `--tag <x>` glob in the mock is what makes the test discriminating: an
unregistered call exits 127 via the dispatcher, so a wrong dist-tag fails the
step rather than silently passing. Repeat for `docker-publish` (push gating),
`csharp-publish` (`dotnet nuget push` gating), and `npm-semantic-release`.
